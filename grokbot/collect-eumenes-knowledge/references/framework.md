# 継続収集と品質評価の運用

## 判断を担う場所

Grok の既存の検索、閲覧、ファイル操作を使う。新しい検索エンジンや常駐処理は作らない。資料と主張の意味を判断するのは LLM、保存・整合性・配分の計算は補助ツールで行う。検索結果キャッシュが必要なのは、検索の繰返しを減らし、候補を選んだ時点を追跡するため。ハッシュ検証が必要なのは、以前の納品で保存本文が欠け、引用位置を再検証できなかったため。

## 二つのモード

| 項目 | 継続収集 | 品質評価 |
|---|---|---|
| 目的 | 価値のある知識を増やす | 手法の性能を測る |
| 候補の追加 | 不足を見て追加できる。失敗は台帳に残す | 開始前に候補・順序・分母を固定 |
| 修正 | 原抽出を残し改訂版を作る | 初回出力を凍結。修正後の点数を混ぜない |
| 配分 | 設定を目安に不足を補う | 評価計画の固定配分を使う |
| 失敗 | 保留・除外・未充足を区別 | 失敗も分母に残し、別の成功例に置換しない |
| holdout | 候補や見本に利用しない | 方法を固定後に一度評価する |

評価用候補と資料の系列（論文の別版、転載、同じ根拠への参照を含む）は評価管理側で記録する。収集側は評価用の内容を読まず、除外用の資料識別子・系列識別子だけを受け取る。holdout を見て方法を変えた場合、旧 holdout は改善用に移し、新しい未使用セットを別に用意する。

このSkillの見本や採用指示を、評価途中で固定済みの抽出指示に追加しない。機械検査の改訂も版を残し、過去の点数と比較するときは同じ検査版を両方に適用する。資料内容を使わない件数・参照の点検と、内容を見た手法改善を区別して記録する。

## 初期配分と検索の選択

設定は AI36・研究20・医療16・生活20・製造8。自己点検済みの採用候補500件を目標にするなら180・100・80・100・40。取得失敗等を含む総候補数は500を超えうる。品質評価の「候補500件固定」とは別である。AI は開発・運用・評価、研究は方法論や研究知見、医療は研究・医療情報や業務、生活は日本の制度と鎌倉〜東京周辺、製造は品質・設計・現場の知識を想定する。これは探索の説明でありキーワード分類規則ではない。

主領域は一つに決め、重複計上しない。副領域や地域は別タグにする。特定サイトで埋め尽くさず、資料種別、発行者、時期、地域、知識の種類の偏りを毎バッチ確認する。構成比を満たすために内容の薄い記録を採用しない。不足が続く場合は、検索の変更と、何が得られなかったかを記す。

## 保存と再開

実行状態は会話だけに置かない。作業領域に以下を保存する。

```text
runtime/<run-id>/
  run.json                  モード、設定と指示のハッシュ、予算、使用量、版
  candidates.jsonl          候補を発行した順の台帳
  events.jsonl              状態変更、試行、判断理由の追記履歴
  checkpoint.json           最後の確定バッチ、次の候補、停止理由
  cache/                    補助ツールが保存した検索結果
  sources/                  取得した原文と抽出テキスト、取得メタデータ
  batches/<batch-id>/
    raw.jsonl
    first_output.jsonl
    excluded_held.jsonl
    validation.json
    coverage.json
    review.jsonl            内容点検の結果。独立か自己点検か明示
  manifest.json             納品ファイル一覧、ハッシュ、欠落、集計基準
```

これらの台帳・チェックポイント・納品ファイルは Bot のファイル操作で作る。補助プログラムが自動生成するのはキャッシュとコマンド出力だけ。自動再開や複数 writer の制御は未実装なので、同一 run は一つの実行者が担当する。

候補台帳には `candidate_id, selected_at, domain, source_url, source_family_id, selection_reason, mode` を記録する。イベントには `event_id, candidate_id, at, from, to, reason, attempt, artifact_paths` を持たせる。状態は discovered → fetched → extracted → self_checked → ready / held / excluded。取得に失敗した候補は fetched を経由させず held にできる。取得失敗でレコードを作れない分は slot 行でも計上し、台帳の同じ候補を別候補として再計上しない。

継続収集でのcandidateは、取得前に選んだ資料または識別可能な資料範囲を一単位とする。同じcandidateから複数の主張を得てもcandidate数は増やさず、record数を別に報告する。配分と初回20候補の上限はcandidate単位。既存の評価計画が別の単位を定めている場合はそれを維持し、この集計と同じ意味の数値だと報告しない。

確定前のファイルは作業用名で書き、参照先の保存と検証が終わってからバッチの確定をイベントに記録する。中断時に原抽出の末尾が途切れていたら、そのバッチを未確定として復旧し、壊れた行を黙って捨てない。納品済みバッチは変更せず、次の版で訂正する。

原抽出の誤りや保留資料の本文不足を含む場合、検査結果の `ok` はfalseのまま残る。`first_output_ok` は採用ファイルとバッチ内整合性の範囲だけを示す。バッチ間の候補重複はcoverageで確認する。出力が0件でもtrueになりうるため件数と併読し、内容点検の結果を別途付ける。検査で見つかった過去の誤りを残すことと、採用候補に誤りを残すことを混同しない。

保留の再取得や改訂は、元バッチ全体の新版ディレクトリを作り、candidate_idを維持する。manifestに `current_batches`（各論理バッチにつき現行版1つの相対パス）と `replaces_batch` の関係を記録する。集計にはcurrent_batchesだけを渡す。旧版は監査用に保存し、新旧を足し合わせない。コードは新版の自動選択や差分適用をしないため、Botが置換関係と台帳を確認する。評価用の初回出力はこの改訂集計に混ぜない。

URL が同じでも内容ハッシュが変われば新版として扱う。版の差分に価値があるか、同じ意味の再収集かは LLM が判定し、旧記録への `supersedes` 等の関係を残す。HTTP取得とPDF等からのテキスト抽出は別に記録し、引用の byte offset は保存した抽出テキストを基準にする。

## 予算と停止

初回の暫定上限は20候補、検索20回、本文取得40回、同一URLは初回込み2試行、30分。いずれかに達したら確定可能な範囲を保存して返す。既存のユーザー指定があればそれを優先する。これは実装済みの強制上限ではなく、Bot が守る運用設定である。

常時運用に移す際は実行環境側で、1回・1日・全体のAPI費用、取得回数、時間、保存容量の上限と再起動間隔を設定する。利用可能な仕組みを確認せず「継続稼働中」と報告しない。課金額が不明な状態で有料APIを新規利用しない。再開時は累積使用量を引き継ぎ、上限を毎回リセットしない。

失敗した取得は種類・試行数・次回時刻を残す。アクセス制限は迂回しない。一つのサイトが失敗しても他の資料を進めてよい。資料の大部分で本文照合不能、記録の破損、予算を把握できない、といった共通原因がある場合は該当処理を止める。同じ原因で再試行する前に、URL・取得方法・待機条件など何が変わったか記す。

## 内容の評価と納品

各バッチで自己点検し、独立評価は別の評価実行または人が行う。初期は1バッチごとに領域・資料種別をまたぐ抽出標本と、取得失敗・保留・除外の標本を評価する。採用だけを見ると過剰除外を検出できない。医療や制度の重要な適用条件、数値、因果方向に誤りが出たら、同じ方法で作った関連記録を再点検する。

本格運用の合格基準は評価開始前に凍結する。既存の500件評価計画が渡されている場合は、その分母と基準を引き継ぐ。今回の補助コードはその評価を代行しない。

納品は JSONL だけでなく、引用先の保存テキスト、取得メタデータ、指示・設定・スキーマの版、候補と失敗の台帳、検証結果、独立評価の有無をまとめる。引用位置の再現に不要なキャッシュ全量まで配る必要はない。本文の再配布可否は根拠付きで別途確認し、保存可と再配布可を分ける。配布できない本文を除く場合は manifest に明記し、完全再現可能とは報告しない。全文・翻訳・引用の扱いを、既存レコードの license 欄だけで確定しない。
