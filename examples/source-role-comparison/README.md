# 資料の役割を回答に明示する比較

**計測済み・新形式は不採用。** 主指標は既存v5が32/32、新形式が30/32。
新規設問は同点、既知設問で悪化したため、既存v5を維持する。
[結果と不採用理由](../../fixtures/experiments/source-role-comparison/2026-10-16.md)、[全応答と採点](../../fixtures/experiments/source-role-comparison/2026-10-16.json.gz)をGitに保存する。
このExampleは比較実験であり、推奨する既定の回答形式ではない。

前段のcheckpointは `1703351`（commit・push済み）。許可規程と補助資料の混同だけを対象に、
既存v5と、資料の役割・許可条件の評価を一つの記録にまとめる候補を比較する。
意味上の役割はLLMが原文から判断する。コードは自己申告した契約・参照・計算の転記を検査する。

## 比較と完了条件

| 条件 | 内容 |
|---|---|
| baseline | 完了済みv5の指示とschema。資料集合と許可規程の評価を別配列で回答 |
| roles | 同じv5入力。資料ごとにroleとassessmentを一緒に回答。補助資料はassessment=null、許可規程・兼用資料には評価を付ける |

モデルはgpt-6-luna / medium。モデルへの質問・原文・観測・計算・原子条件表示は両者で完全に同じ。
既存のSDK、抽出、SQLite、計算、参照監査、主判定採点を再利用する。
runnerの固定コード・失敗キャッシュ・再開の仕組みはlinked-answer-holdoutから引き継ぐ。
抽象化のために既存のrunnerや本体を変更しない。

- 既知4問は保存済みの抽出contextを使用。O04/AC04の混同、CP02の説明、FG02の許可を回帰確認。
- 新規4資料群12問はライブ抽出。表題と役割の不一致、兼用資料、補助資料の別件の条件、同格規程の競合を含む。
- 各2反復、2条件、順序反転、2並行。最大4抽出＋64回答。各120秒。自動再試行・回答差替えなし。
- 主指標は最初の回答で、判定・適用資料集合・許可規程の評価集合/結果・既存監査がすべて合うこと。
  両方式へ同じoracleを用いる。役割ラベル自体の一致は候補側だけの副指標で、主比較に混ぜない。
- 新規問の主指標が改善し、誤許可が増えず、判定一致と既知問の主指標が悪化しない場合だけ採用候補にする。
  同点なら追加効果未確認。共通の既定方式へは自動昇格しない。
- 抽出や接続の失敗を予定分母から落とさない。全説明も別途点検する。
- 生要求・応答・失敗・使用量を保存し、入力一致・正解非提示・コード不変・追加呼出し0での再生を確認する。
- 計測後に結果と残件を追記し、比較に使ったコードと持ち運べる結果要約をcommitする。

期待する資料の役割はfixtureにだけ置く。文書名、ID、固有の質問語句で役割を決めない。
既知の悪い回答は回帰試験だけで使う。新規問題はこのプロトコルの出力を見る前に固定する。
同じ作成者の合成問題で、独立の人手評価や実資料の受入ではない。反復と同じ資料群の問題は相関する。
指示と出力契約の組全体の効果で、roleフィールドだけの効果は分離しない。
抽出拒否の救済・本体契約・DB・既存v5・以前の比較結果の変更は対象外。

## 実行

```sh
bun test test/eval/source-role-comparison.test.ts
bun run verify
bun run build
bun examples/source-role-comparison/main.ts --prepare-only
```

表示されたrunの固定コードから実行する。再開も同じ場所を使う。

```sh
bun <run>/frozen-code/examples/source-role-comparison/main.ts --resume <run>
```

実モデルを呼ぶ前に部分→全体verify→buildを確認する。通常verifyはモデルを呼ばない。
完了後、同じコマンドをキャッシュだけで再実行し、report/events不変を照合する。
