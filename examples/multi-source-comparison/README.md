# 複数資料・更新・条件の比較実験

同じ資料全文をそのままLunaへ渡す場合と、全文にWorldModelのSlice・条件判定を
加える場合を比較する。前回の単一資料比較より難しい状況で、回答の差を調べる。
この実験は `examples/` 内で閉じ、製品コード・隣接プロジェクト・984件のseedを変更しない。

## 固定するもの

- 架空の15資料、4分野、16問。各問2回、2条件で64回答。
- 本番配信：撤回・訂正、将来の施行日とその境界、決裁権のない新しいブログ。
- 製造：同格の未解決の矛盾、結論が一致する範囲、別工場の適用範囲。
- 医療研究：訂正された閲覧規程、未承認草案、AND・OR・否定と情報欠落。
- IT運用：同順位の相反する観測、1時間を超える古い観測、ORで補える欠落、否定対象の欠落。

正解を確定できるよう資料は合成した。実際の医療・製造・運用の指針ではない。
実資料984件の収集品質や、その検索の良し悪しを測る実験ではない。
質問・正解・指示・資料・モデル・実験コードのdigestはモデル実行前に固定する。
同じ問の2回と同じ資料群内の質問には相関があり、64回答を独立64例とは数えない。

## WorldModel側の作り方

1. 回答用の質問と正解を見せず、Lunaに資料群を一括解釈させる。
   各資料の引用付き候補、条件式、有効期間、明示的な撤回、未解決の矛盾を得る。
   日付だけの優先順位や適用範囲の判断をコードで代替しない。
2. 既存の抽出validatorとJSON Pointer引用検証を再利用する。追加の参照は実在する
   先行資料に限り、日付は明示的なUTC値を外部表現から変換する。
3. `test/support`の一時SQLiteに公開APIで候補を保存する。矛盾の参照、施行時刻を
   過ぎた撤回を記録し、同一操作の再投入がno-opになることを確認する。
   明示的な「撤回して置換」の資料は旧候補のretractと新しい独立候補で表現する。
   `supersede`で同一主張の版を差し替える経路や、採用・dispute遷移は今回試していない。
4. 公開APIでSliceを作り、既存の三値条件判定を実行する。
   候補の採用は行わず、authorityの意味的な正しさをvalidatorが保証するとは扱わない。
5. 両条件に同一の資料全文・観測値・質問・共通指示を渡す。
   World条件だけ、実際に保存・投影した結果と条件判定を追加する。
   観測キーの日本語の定義、基準時刻と観測時刻のISO表示・epoch値も両条件に渡す。
   時点ごとに別の一時DBへ、その時点までに発効する撤回を再生する。
   同じDBを長期間更新する運用や、過去時点への自動的な巻戻しの検証とは区別する。

これは「Lunaによる事前整理＋WorldModelの状態管理・条件計算」の経路全体との比較。
整理だけを追加する第三条件はないため、差が出ても全てをWorldModel単体の効果には帰せない。
資料の選択は固定で、検索・トークン節約・長期運用を比較しない。

## 採点と実行

主指標は事前に固定した `allow / deny / hold` と、現在の判断を支配する資料IDの集合。
判定の正しさと資料集合の一致を別々に数え、両方が一致した件数も出す。
集合には撤回・未施行・草案・非公式説明を含めない。文章でそれらに言及するのはよい。
出力schemaのID列挙は提示資料に限定する。どのIDを選ぶかはLunaが判断する。
共通ランタイム方針は指示であり、架空の資料IDを付けて引用しない。
運用の観測値の有効性を規定するO2も、当該判断の根拠に含めるという採点規約にした。
資料集合の完全一致は厳しいので、判定が正しいが補助資料を挙げない回答とは区別する。
説明文は全回答を読んで別途点検し、点数の変更には使わない。LLM採点器は使わない。

v3以降は、主張とその実際の計算結果を同じ要素に結合して提示し、回答を
`governingSources → assessments → explanation → decision` の順で要求する。
最後の判定へ進む前に、選んだ規程の計算結果と説明を一致させる指示に変更した。
これは短い根拠の記録であり、モデルの内部思考の出力を求めるものではない。
適用規程と権限・範囲の解釈は引き続きLunaが担う。

`grounding.ts`は、Lunaが選んだ規程について、参照先・計算結果の転記・自己申告した
各規程の結果と最終判定の対応を検査する。回答の書換え、再試行、適用規程の選択、
原文の意味の判定は行わない。転記が一致しても、適用規程の選択や説明文の正しさは保証しない。
計算の表現が原文を再現していないとモデルが主張した場合は、具体的な理由を
`overrideReason`へ残させ、通常の一致として数えず別に報告する。
従来の主指標は変えず、最初の生回答をそのまま採点する。

出力形式の保証と内容の正確性は別であるため、型に合うだけでは成功としない。
参考：[OpenAI Docs — Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)。

SDK・ログイン・隔離機構は `seed-luna/luna.ts` を再利用し、`gpt-6-luna / medium`。
抽出・回答とも毎回新しい会話。ツール・検索・作業フォルダへのアクセスを無効にする。
回答順は交互に反転し、一方が常に先にならないようにする。

```sh
bun test test/eval/multi-source-comparison.test.ts
bun run example:multi-source --prepare-only
bun run example:multi-source --resume artifacts/multi-source-comparison/<run>
bun examples/multi-source-comparison/render.ts --run artifacts/multi-source-comparison/<completed-run>
```

`--prepare-only`は正解と指示の固定だけを行い、モデル抽出や回答の成功とは数えない。
`--resume`は同じ指示・入力・実験コードに限って保存済み応答を再利用する。
成功応答は上書きせず、失敗はeventsへ残す。失敗した呼出しだけを再実行できる。
自動で採点基準やプロンプトを調整する処理はない。
既存の完了runから抽出を固定して使う場合は、準備・実行・再開すべてで
`--extraction-run artifacts/multi-source-comparison/<completed-run>` を指定する。
資料・抽出指示・schema・モデル・応答digest・実際のrequest digestを照合する。
再利用時の抽出使用量と時間は元の値であり、新しいモデル呼出し費用とは区別する。

出力は `artifacts/multi-source-comparison/<run>/`。
`protocol.json`、`cache/*-request.json`、生応答、`contexts.json`（保存履歴含む）、
`events.jsonl`、`report.json`を保存する。利用量・所要時間は抽出と回答を分ける。
World条件は全文に整理結果を追加するため、入力が増える設計である。
