# 有効期間外の計算理由を用いた監査比較

既存v5・構造監査・本体src・抽出・計算・採点・過去の比較を変更しない。
今回の目的は、時刻を誤読しても評価と判定が一致すれば監査を通る問題について、既存の計算理由を再利用して検出・修正できるか測ること。
`system-context-engineer`の比較手順を継続し、意味判断はLLM、コードは既存の計算との契約検証だけを担う。

## 実測結果

[2026-10-16の結果](../../fixtures/experiments/validity-audit-comparison/2026-10-16.md): 45呼出し・108結果を取得。既知の期間外選択8結果を検出し6結果を修復、残る2結果を拒否。未見24結果では期間外選択が発生せず、新規検出の効果は未確認。事前採用条件は未達で、v5を維持し比較資産として保存した。以下は実測前に固定した計画であり、測定後の条件変更はしていない。

## 実測前の固定計画

監査は、回答が許可規程として選んだassessmentsを、sourceIdとassertionIdで既存World unit/evaluationへ結び付ける。
その計算理由に`CLAIM_NOT_VALID`があれば、有効期間外の許可規程を選んだ不整合として不合格にする。
これは既存の`evaluateConditions`が主張の有効期間を判定した結果を使う接続であり、コードが日付や説明文を解釈して適用資料を選ぶ実装ではない。
`violated`だけ、`CLAIM_VALIDITY_UNKNOWN`、対象範囲の不成立、無関係なWorld unitはこの追加検証で不合格にしない。
原文の抽出が誤っている可能性は残り、その訂正は別の問題。勝手なoverrideで監査を通さない。

governingSourcesを一律に検査しない。旧資料の観測章が引き続き適用される場合があり、許可規程の評価と資料引用を区別する。
説明だけの時刻誤記、権限・対象範囲・必要な資料の欠落は、この追加検証が保証する範囲ではない。

同じ初回回答から3方式を比較する。

- baseline: 既存v5の初回を保持し、旧構造監査で扱う。
- control: 新旧を合わせた監査が不合格のときだけ1回見直す。旧監査結果だけを渡す。
- validity: 同じ発動条件で1回見直し、旧監査に加えて有効期間外の指摘を渡す。

両見直しの開発者指示、原文・計算・初回、schema、回答順序、呼出し回数は同じ。違いは追加監査のフィードバック。
これは旧方式そのままのcontrolではなく、追加呼出しの有無を揃えた比較である。
合格時は文字列を変えず保持。見直し後も新旧の監査を記録し、controlのacceptedは旧監査、validityのacceptedは新旧両方の合格とする。
acceptedはこの契約の合格であり、意味の正しさや公開許可ではない。不合格出力も採点用に保存し、拒否と正しい回答を混同しない。
再見直し、抽出/通信の再試行、初回への差替え、資料ID分岐、期待値による発動は追加しない。

既知6保存回答×2反復: 前回TC01/0の初回・通常見直し・重点指示の3誤答、KR07の保存誤答、正しいKR08、説明だけの時刻誤りがあるTC04/1。
前4件は有効期間外の検出・修復、後2件は不変更の制御。3件は同じ設問の異なる出力で、独立した3設問ではない。既知初回は新規v5生成ではない。
未見は新規3資料群7文書12問×2反復。施行直前・時刻ちょうど、期限満了、ミリ秒境界、通常の不成立、不明、別対象範囲を含む。
抽出は各群1回、SQLite入力と初回v5を全方式で共有する。全原文・計算を保持、期待値は渡さない。資料群・設問の識別子は実行前に検査する。
合計36件/方式、108セル。上限99呼出し＝3抽出＋24初回＋最大72見直し。2並行・各120秒、見直し順は反復ごとに反転。

主指標は従来の判定・資料集合・許可評価集合/結果・旧構造監査の全一致を維持する。
別途、新監査による検出、正解への誤警告、acceptedの誤答、修復成功、費用を計測する。
新監査を比較用の任意チェックとして保持する条件は、全件完了、既知4誤答を全て検出、正しい初回への誤警告/正しい出力の拒否0、未見でも旧監査が見逃した有効期間外の誤答を1件以上検出すること。
修復方式の保持には、加えて既知を全反復で正解に修復、合格制御を文字列不変、初回の主指標/判定正解を壊さず誤許可/撤回混入を新設しない、未見の純改善と2資料群以上で純改善を要求する。
フィードバックをcontrolより優先するには、さらに未見で純改善しcontrolの正しい主指標/判定を保持すること。同点なら指摘固有の効果と言わない。
いずれもv5は既定のまま。抽出/通信失敗は予定分母に残し、部分成功を全件受入としない。

## 必要作業・完了条件

1. 旧監査の見逃し、未来/期限終了、始点包含/終点除外、不明、通常の不成立、参照不一致、説明のみの誤記、合格時不変更、1回上限、正解非提示を部分試験。
2. SQLite結合、全体verify/buildを確認して実行コード・資料・指示・期待値・採否を固定。
3. 実測中は編集せず、抽出・全回答・説明・費用を確認。追加呼出し0で再生、SQLite再構築と全分岐/採点/監査/採否の再現試験を追加。
4. 結果・採否・限界・進捗を保存し、全体verify/build、担当外・意味判断代替の差分点検後にcommit/push。

同一作成者の合成資料であり、独立盲検・実資料の受入ではない。通常verifyはモデルを呼ばない。

```sh
bun test ./test/eval/validity-audit.test.ts ./test/eval/validity-audit-measured.test.ts
bun run verify
bun run build
bun examples/validity-audit-comparison/main.ts --prepare-only
bun <run>/frozen-code/examples/validity-audit-comparison/main.ts --resume <run>
```
