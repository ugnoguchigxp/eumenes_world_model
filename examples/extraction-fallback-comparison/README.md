# 抽出拒否の回復比較

**計測済み・既定採用は保留。原文切替は不採用。再抽出は判定56/56だが資料集合が51/56で、実験として保持する。**
[結果](../../fixtures/experiments/extraction-fallback-comparison/2026-10-16.md)を参照。

既存v5は変更しない。`recovery.ts` はExample内の任意の入口で、候補が
`HYPOTHETICAL_NOT_FACT` で拒否された場合、または候補0件の場合だけ、全原文を
既存v5のsource-only形式に渡す。正常時は既存interpret/persist/contextsを使う。
原文に対する適用判断は引き続きLLMが行う。拒否候補を事実化せず、拒否理由は
実行記録に残す。文書名・設問・期待値による実装分岐はない。

一部の計算だけ残すと、抽出できなかった改訂・撤回・対立規程を回答から
脱落させる恐れがある。この比較では資料群全体を原文回答へ切り替え、元の文書を
一つも落とさない。条件計算をLLMが担うため、正しさを別途測定する。
これはWorld候補の受理拒否からの復帰であり、プロバイダーの安全拒否や通信失敗を
回避するものではない。原文そのものが欠ける場合も対象外。

## 作業と完了条件

1. 保存済みの実失敗DS3を再現し、正常時・重要資料拒否・全件拒否・候補0件を検査。
2. SQLite結合で正常時の入力と計算がv5と同一、拒否時は全原文が残ることを確認。
3. 期待値・指示・コードを固定し、同じ抽出応答でstrict-v5/fallback-v5を比較。
4. 新規設問の初回回答を2反復で記録。失敗・未回答は分母に残す。
5. 全体verify/build、結果の再生と差分点検後、計測結果とともにcommit/push。

範囲は新Example・回帰試験・結果記録のみ。本体、公開契約、DB schema、既存v5、
隣接repoは対象外。新依存は追加しない。これを製品結合完了とは扱わない。

## 比較設計

5条件×4問×2反復×2方式=80セル。strictの抽出拒否32セルはモデルを呼ばず
停止として記録。残り48回答のみ実モデルを呼ぶ。回答指示とschemaは両方式とも
既存v5をそのまま使う。正常条件は入力も一致。抽出の新規呼出しは0。

- 実失敗: DS3未承認提案のhypothetical拒否。既知4問。
- 拒否注入: DS2改訂規程もhypotheticalにする。新規4問、撤回境界を含む。
- 拒否注入: airlock全候補をhypotheticalにする。新規4問、OR・欠落を含む。
- 空候補注入: studio-accessの同格規程DK6を空にする。新規4問、対立を含む。
- 正常: mixed-vault。新規4問、別区域・明示false・AND短絡を含む。

初回に新規作成した16問のうち、FA04・FC01・FN01の観測条件は既存設問と重複した。
未見の観測条件は13問として分けて報告する。文書は以前の実験で抽出したもの。
拒否注入は障害時の試験であり自然発生率の測定ではない。inputs.jsonは原応答を
保存し、fixtures.tsで注入箇所を明示。注入内容・正解・分類は回答モデルに渡さない。

主指標は判定・適用資料集合・許可規程の評価集合/結果・既存出力監査の全一致。
採用条件は、実失敗8セル全回復、注入24セル全主指標一致、誤許可0、正常8セルの
入力一致とペア悪化0。原文回答の監査成功はnative計算の転記成功を意味しない。
説明の事実性は結果記録時に別途目視点検する。

## 実行

```sh
bun test test/eval/extraction-fallback.test.ts
bun run verify
bun run build
bun examples/extraction-fallback-comparison/main.ts --prepare-only
bun <run>/frozen-code/examples/extraction-fallback-comparison/main.ts --resume <run>
```

通常のverifyはモデルを呼ばない。実行コード・依存・期待値をprotocolへdigest付きで
保存し、独立SDK thread、同じモデル/medium、2並行、ペア順序反転で実行する。
初回応答を保存し、失敗の再抽選はしない。resumeは成功・失敗キャッシュをそのまま
使い、同一protocolのみ許す。計測中の編集は禁止。結果が採用条件を満たさなければ、
候補を既定にせず、失敗を残して次の仮説を検討する。

## 第2ラウンド: 抽出を1回だけやり直す

原文切替は40回答完了、判定38/40・主指標36/40。FC03のOR誤計算とFC04の
説明/評価不一致が2反復とも発生し、事前の採用条件を満たさなかったため不採用。
この失敗を受け、`retry.ts`で資料への帰属を持つreported候補として再抽出する。
コードがmodalityを書き換えることはない。候補は通常のvalidate/interpretを通す。
拒否資料に依存する改訂・撤回も再解釈する必要があるため、対象は資料群全体。
再抽出は1回だけ。再度拒否や通信失敗なら止まり、原文回答へは降格しない。

第2ラウンドの元20問は開発ケースとして扱い、新しい観測条件8問を追加する。
追加8問は以前の全fixtureと条件重複がないことを試験する。合計28問×2反復×2方式
=112セル、strict停止44、実回答最大68、再抽出最大4回。新規8問の期待値は
実行前に固定。事前採用条件は実失敗8セルと注入36セルの主指標全成功、誤許可0、
正常12セルの入力一致・ペア悪化0。失敗した場合は3回目の調整を無条件で行わない。

```sh
bun examples/extraction-fallback-comparison/main.ts --recovery reextract --prepare-only
bun <run>/frozen-code/examples/extraction-fallback-comparison/main.ts --recovery reextract --resume <run>
```

初回の厳密再生には初回runに保存したfrozen-codeを使う。第2ラウンドの指示・実装・
新規設問を固定した後は、結果確認まで編集しない。両runの生応答・失敗は保存する。
