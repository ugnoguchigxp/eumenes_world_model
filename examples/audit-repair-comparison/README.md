# 既存監査を使う1回の回答修正

**実測済み・新規採用保留。既存v5は維持。**
保存済みの監査不合格6回答×2反復は、監査結果あり/なしとも12/12で修正成功。
未見は24/32が初回から正解で修正発動0、残る8件/方式は抽出拒否。
既知改善を確認した比較用実装として保存し、未見優位と監査フィードバック固有効果は未確認とする。
[結果・採否・限界](../../fixtures/experiments/audit-repair-comparison/2026-10-16.md)を参照。以下は実測前の固定計画。

目的は、説明では正しい規程を述べながら評価・資料欄で別規程を選ぶ失敗を、既存の監査を使って改善できるか確かめること。
既存v5、本体src、公開契約、DB、抽出・計算・採点・監査そのもの、前回実験は変更しない。
`system-context-engineer`の比較手順を継続し、意味判断はLLM、コードは監査契約と1回上限の強制だけを担う。

## 実測前の計画

新規4資料群14文書16問を2反復し、既存v5の初回32回答を生成する。同一の初回回答から3方式の結果を作る。

- baseline: v5初回をそのまま残す。
- control: 既存監査不合格時だけ、原文と初回回答を渡し1回見直す。監査結果自体は渡さない。
- audit: 同じ条件・指示・schemaで1回見直し、既存監査の結果も渡す。

修正指示は、原文の適用範囲/時点に戻って規程・評価・資料・説明・判定を揃え、誤選択した規程へ判定を合わせるだけで済ませないこと。
監査と前回答もデータであり正解ではない。フィードバック以外の修正指示はcontrol/auditで同一。
両者は同じ初回回答を使うため、初回生成の偶然の差を改善として数えない。修正呼出し順は反復ごとに反転、2並行。
合格時は修正せず文字列を維持する。修正後も再監査し、不合格はrejectedとして保存し再修正しない。
通信失敗時は元回答へ戻して成功とせず、失敗を残す。取得した不合格応答も評価用に保存する。
acceptedは既存監査合格だけを意味し、意味上の正しさや本番公開を意味しない。

既知8件は保存済み回答を初回として使用（新規v5回答ではない）。
SD01の3失敗、NP01の指示だけの失敗、CV04の資料欠落、CP02の計算転記誤りを各2回修正対象にする。
監査が見逃すNP01の誤った不許可と、正しいRV03を合格時不変更の制御として残す。
複数件が同じ設問に由来し、反復も相関する。既知の回復率を未見の生成品質と混同しない。
既知16＋未見32=48結果/方式、3方式で144セル。最大124呼出し（4抽出＋32初回＋88修正）。
各呼出し120秒。監査以外の採点・期待値で修正を発動しない。抽出/通信再試行、回答修正の反復、資料IDによる処理は追加しない。

新規群は庇の施行切替、搬入口の旧観測章存続、試料機のOR→ANDと全文撤回、区画別散布条件。
原文・計算・観測は全保持。新規抽出は各群1回、正解はモデルに渡さず、失敗を全方式の分母に残す。

主指標は従来どおり判定・適用資料集合・許可評価集合/結果・既存監査の全一致。
保持条件: 必要呼出しと全セル完了、既知の監査不合格6件を両反復で正解、合格制御2件を文字列不変、
初回の主指標正解/判定正解を壊さず誤許可/撤回混入を新設しない、未見で純改善かつ新規2資料群以上で純改善。
監査フィードバックを優先するには、さらに未見でcontrolに改善数>悪化数、controlの正しい判定を壊さないことが必要。
controlと同点なら、監査結果を渡す固有の効果とは言わない。既知の修復だけでも未見優位とは言わない。
どの場合も既定v5は維持。候補の採用と監査の意味判定能力を同一視しない。

## 必要作業・完了条件

1. 保存された失敗と監査見逃しを再現。発動条件、1回上限、監査フィードバック以外の同値、正解非提示を部分試験。
2. SQLite結合、verify/build後にコード・指示・資料・期待値・採否を固定。
3. 1回の実測で全初回/修正/失敗を保存し、説明・抽出・費用を確認。実行中は編集しない。
4. キャッシュ再生で追加呼出し0と結果不変。SQLiteからの入力再構築、全採点/監査/分岐を再現する試験を追加。
5. 採否・限界・進捗を保存、全体verify/buildと担当外/意味判断代替の差分点検、commit/push。

通常verifyはモデルを呼ばない。独立/盲検/実資料の受入ではなく、同一作成者の合成資料である。

bun run verify
