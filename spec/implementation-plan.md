# Eumenes WorldModel 実装計画

2026年10月9日改訂。Solが作業票単位で実装・検証できるよう、契約、所有ファイル、依存順、失敗時の動作、受入ケースを固定する。**現在の実装済み範囲はP0だけ。この改訂は文書の変更であり、P1以降を実装したものではない。**

## 読む順序と正本

1. この文書で対象段階と着手条件を確認する。
2. [実装契約](plan/contracts.md)で値・状態遷移・SQL所有・同期APIの規則を確認する。
3. [P1とP2の作業票](plan/core-tasks.md)、または[P3からP6の作業票](plan/integration-tasks.md)の該当票を読む。
4. 票に記された[受入ケース](plan/acceptance.md)を先に試験へ起こす。
5. 完了時に[実装進捗](plan/progress.md)へ実際の証拠を記録する。

製品の目的と五要素は[全体設計](world-model-design.md)を継承する。将来実装の具体的な順序・API・所有境界については本計画と実装契約を優先する。現在存在するファイル・コマンドは[プロジェクト構造](project-structure.md)、現在の試験hostは[SQLite接続](sqlite-testing.md)を正本とする。将来のファイルを既存として扱わない。

## 完成させるものと所有境界

独立したTypeScriptパッケージとして、対象、根拠付き主張、条件、時間、因果・相関・依存、判断用Slice、予測照合、訂正・忘却を実装する。Eumenesへ組み込む際は既存の単一Writerから借りた接続を使い、原典の版検査・Memory依存登録・World更新・回答採用を一つのホストtransactionに載せる。

| 所有者 | 所有するもの | 所有しないもの |
|---|---|---|
| Worldの各domain | 意味規則、固有契約、所有world_表のSQL・migration、固有試験 | 他domainのprivate実装・表の直接操作 |
| Worldのapplication層 計画追加 | domainの公開同期操作の順序、共通ガード、複数domainの更新調整 | DB接続、transaction、queue、HTTP、モデル呼出し |
| WorldのSQLite基盤 | 借りた接続型、migrationの固定順集約 | 業務SQLの集約 |
| Eumenes | 単一Writer、認可、source/Goal/実行状態、queue、推論、journal、回答公開 | Worldの意味処理の複製 |
| Memory | 原典・本人State・自分の忘却と外部依存登録 | World主張の正本 |

application層はP2-04で追加する予定。現行P0には存在しない。複数domainの更新をlifecycleへ集中させると循環するため、上位の薄い組立て層へ置く。純粋APIは引き続きdomainが所有する。

今回および本体だけの実装依頼では、隣接リポジトリ、製品DB、既存設定、秘密、データ移行、公開・配布先を変更しない。P3以降のホスト変更は、後続依頼の対象にEumenesが含まれる場合に実施する。承認済みの範囲を作業票ごとに再確認する必要はない。

## 段階と実施順

| 段階 | 作業票 | 段階終了時の成果物 | 終了時に主張してよいこと |
|---|---|---|---|
| P0 完了 | P0-01〜07 旧計画 | 8domainの予約、SQLite試験host、検証ツール | 開発準備の検証が可能 |
| P1 未着手 | P1-01〜11 | 固定契約とIOなしの意味処理 | 合成fixtureで意味規則が成立 |
| P2 未着手 | P2-01〜10 | 所有SQL、原子的更新、忘却、再構築 | 独立した実SQLiteで保存・失効が成立 |
| P3 未着手 | P3-01〜09 | 配布物、Source/Memory/Goal接続、Broker、回答採用 | Eumenes単一Writerを使う縦断ケースが成立 |
| P4 未着手 | P4-01〜05 | Local抽出、永続進捗、取消・再開、日本語評価 | 実モデル評価を含む継続構築が成立 |
| P5 未着手 | P5-01〜04 | 判断APIの利用、訂正UI、予測実測の一巡 | 一つの実仕事で判断と実測がつながる |
| P6 未着手 | P6-01〜04 | 外部知識・能力接続、複数Scope、長期受入 | 個別に記録した運用条件で受入済み |

P1→P2→P3→P4→P5→P6を基本順とする。票に記す先行票が未完了なら依存する実装へ進まない。外部契約待ちでも依存しない票は進めてよい。段階全部を一括変更するのではなく、一票ごとに動作と検証を閉じる。P1の時点で五要素とscenarioの純粋規則まで作り、P5ではその製品利用を実装する。

## Solの一票の進め方

1. 進捗表から対象票を選び、先行票の結果と変更許可範囲を読む。設計案にある名前と現行exportを照合する。
2. 票の「変更先」を実ファイルへ対応付ける。指定された新規ファイルは作成可能。補助ファイルは同じ所有domain内へ置く。別domain・公開契約・SQL所有を変える必要が出た場合は先に契約差分を記録する。
3. 入力と期待値を受入ケースから試験へ起こし、対象機能が未実装なら失敗することを確認する。既存P0の試験だけで完了にしない。
4. 必要な最小実装を行う。依存を初めてimportした時点でscripts/domains.tsへ直接依存を追加する。禁止importを通すために検査を緩めない。
5. domain試験、全体verify、buildを実行する。schema・公開契約・forget・配布変更なら横断試験と該当consumer試験も実行する。
6. 外部接続や実モデルを実施していない場合、fixture結果とは別に未受入と記録する。合格扱いのstub、全skip、0件、未適用migrationを成功にしない。
7. 進捗表に変更ファイル、コマンド、試験数、受入ケースID、結果、残る制約を追記する。対象票の完了条件をすべて満たした場合だけ完了へ変更する。

一票がさらに分割を要する場合は`P2-04.a`のように子票を作り、親票は全子票完了まで進行中とする。元の受入ケースを削らない。時間不足を機能の省略で埋めない。

## 推測してはいけない外部契約

| ゲート | 必要な証拠 | 未取得時の対応 | 所有票 |
|---|---|---|---|
| G1 Memory共有型 | 固定版配布物、公開SourceRef/AccessContext、digest、standalone install | 公開ソースから固定配布物を生成。生成不能ならG1依存票を待機し、独立票を進める | P1-02 |
| G2 ホスト更新 | 現行Writer/queue/dialogueのexportとtransactionの確認 | 旧Continuityや未存在APIを仮実装しない | P3-02 |
| G3 sourceとGoal | 版・Scope・訂正イベント・GoalSnapshotの公開契約 | 明示的にmissing/unknownを返す。常に許可するAdapterは禁止 | P3-03、04 |
| G4 忘却と復元 | 両journalの耐久化手順、再登録・restore epoch・起動gate | World利用を閉じ、永続受入を未完了とする | P3-05 |
| G5 実モデル環境 | 登録されたLocal Provider、モデル版、実行予算 | deterministic試験まで実施。実モデル成功と書かない | P4-05 |
| G6 外部知識・能力 | 不変版・削除・Scope・実行結果の公開契約 | 永続根拠に使わず一時参考、または当該接続を無効化 | P6-01、02 |

これらは現在存在しない契約を創作しないための着手条件であり、すべてをユーザーへの追加確認に変える指示ではない。既存コードと配布物で解決できる事項は自分で確認する。必要な外部変更が依頼範囲外なら、その票の必要変更と理由を具体的に残す。

## 検証コマンド

現在利用可能なコマンドは次のとおり。domain試験がまだない8領域の指定は失敗する。

```sh
bun install --frozen-lockfile
bun run verify:all
bun run build
bun run test:sqlite
bun run test:domain conditions
bun run verify -- --domain conditions
```

最後の二つはconditionsの実装試験追加後に成功する。domain指定でも整形・lint・型・境界は全体を確認し、試験だけを絞る。全体verifyは現在22試験の基準を保つ。試験の統合・置換は同じ保証をより強い試験で満たす説明がある場合に限る。

作業票の「検証」で`D(name)`は`bun run verify -- --domain name`、`F`は`bun run verify:all && bun run build`、`S`は`bun test ./test/scenario`を表す。Sは最初の横断試験をP2-04で追加してから利用する。追加予定のpack、bench、evalコマンドは作成票を明記し、現時点で存在すると扱わない。

複数domainを変えたらDをすべて実行する。文書だけの変更ではコード試験を追加せず、参照先・作業順・ケースの網羅を検査する。

## 仕様変更と完了の扱い

未確定事項を解決した場合は、実装前に本計画の契約へ反映し、理由・影響する票・追加試験を記録する。特にSourceRefの意味、scope境界、状態遷移、同じ操作キーの扱い、schema互換、忘却保証をSolの裁量で変更しない。

`ready`は資料の正しさや現実の真実を保証しない。`active`は採用状態である。SQL試験成功はWriter queue結合成功ではなく、fixture成功は実モデル品質の証明でもない。この区別を進捗と最終報告で維持する。
