# 残る改善の実施範囲（2026年11月7日）

目的は、既存実装を作り直さず、未達の原因を調べられる診断と、更新を含む比較を
実行可能にすること。実装・fixture・実モデル・製品受入を区別する。

## 重複を除いた作業と依存

1. 抽出の既存採点を保持し、最初の誤候補だけでは見えない不一致、抽出不足、
   validationによる保留、区分誤りを内容なしの診断へ追加する。診断は評価専用で、
   モデルの入力・製品のルーティング・正答補修には使わない。
2. 同じ原典と同じ予算からraw/plain/Worldを比較する時系列episodeを固定する。
   更新、条件不足、撤回、忘却を含め、誤再断定・判断変更・保留・費用・欠測を
   集計する。既存の抽出・SQLite replay・回答・採点・API予算機構を再利用する。
   fixtureは基盤の検証だけに用い、実モデルの優位や長期稼働の証拠にしない。
3. 既存workflowを公開mainの正確なSHAで実行し、結果を保存する。
4. 部分→結合→verify/build、差分と過去証拠の不変を点検し、progressへ記録する。

## 再実装しないものと境界

- 初期同期backfill、SIGKILL復旧、複数引用、Outcome訂正とreceipt失効は実装済み。
- source由来candidate rootのhost補完も既存。別host/state由来入力を増やす際は、
  root供給の契約と実際の入口を先に受け入れる。新索引は測定根拠なしに追加しない。
- 隣接repoは参照専用。製品DB・設定・秘密・稼働hostは変更しない。
- 実Runtime台帳の公開契約と必要なhost変更の範囲が先行するため、cache-latencyの
  本番相当の実行をfixtureで代替しない。予測・実測の数値を作って埋めない。
- APIの累積上限10 USD、既存上限9.93184335 USDを維持。今回はAPI呼出し0。
  95%・0許容違反・旧gold・既存の改善5件条件と過去結果は変更しない。
- commit/push/main統合は行わない。main CIとローカル変更の検証は別SHAとして扱う。
