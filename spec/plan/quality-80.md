# WorldModel 技術品質80点に向けた改善計画

2026年11月5日。前回レビューの技術品質 **暫定69.7点** を出発点とし、同じ評価基準による再評価で **正式80点以上** を目指す。Claude APIとOpenAI GPT-6 Luna APIを、抽出・根拠選択・回答・意味評価の比較に使う。

指摘の修正に加え、契約の境界、途中失敗、並行実行、配布、導入・復旧を実行証拠で確認する。すべての目標アンカーが成立した条件付きシナリオは **80.4点**。これは達成予測や現在の点数ではなく、必要な証拠を揃えた場合の計算値である。点数に届かないときは基準を変更せず、未達の項目と次の条件を報告する。

計画作成時点では個人シェルのAPIキー参照設定までを実施。その後の利用者の明示依頼により、ローカルmainと既存の未コミット変更を前提に改善・有料比較・再評価を実施する。実績と未受入事項はprogress.mdへ追記する。

実行時の費用上限は利用者指定の**合計10米ドル**。モデルは利用可能性を確認済みの`gpt-6-luna`と`claude-haiku-5-5`、共通の費用台帳で全runを合算する。以下のSonnet/150ドル/3612要求は当初の提案・最大構成の記録であり、追加支出許可ではない。現行の接続・生成条件と残件は実績欄を正本とする。両社とも非制約JSONで最初の生成を既存検証器へ渡す。Claudeのschema非対応・grammar過大を理由とし、片方だけのfallbackや意味修復は行わない。

### Q01 鮮度情報

再現は、原典が現行であるactive主張の観測時刻だけを変え、投影のfresh/staleと探索の出力を比較する。現在はReasoningEdgeが鮮度情報を持たず、古い主張も条件充足の `confirmed:true` を返せる。`confirmed`は真理の証明ではないため、この語だけを変えて完了にしない。

最小案は、既存の鮮度・根拠検証状態をedgeから経路・依存・Gap・scenarioへ運ぶ契約。staleを一律falseへ変えるのではなく、利用可能性と不確かさを明示し、意味上の採否はhost/LLMに残す。source変更、反証、撤回、期間外、条件不明も別理由として保つ。契約変更はcontracts.mdを先に更新し、公開型と旧consumerへの影響を確認する。

### Q02 忘却の到達

最初に既存hostがsource/stateに対応するcandidate rootを漏れなく渡すか確認する。これで成立する場合、索引追加は行わない。成立しない場合はreceive時から依存参照を同じtransactionで登録する最小案を契約化する。新migration、既存行のbackfill、途中失敗・再構築・restoreも同じ票に含め、本文を索引表へ複製しない。

全inbox状態、manifestなし、複数source、拒否候補、処理中断と再起動、古いDB＋新journal、遅着・再送を確認する。World内の `complete` とhost全体の削除確認を混同しない。外部確認未了はgateを閉じたままにする。検証する消去はアプリケーションから読める本文と再利用・復活であり、WALや媒体の物理消去を保証したと表現しない。

### Q03 配布と保守

配布文書を実際のpack方針へ合わせ、Memory型要件と両tgz導入を明記する。本体・同梱物・評価資料の所有者、出自、適用される利用・再配布条件を記録し、権限のないライセンスを新たに宣言しない。権利確認が残ればUnknownのままにする。

固定版・hashを維持し、脆弱性情報は版、実際に使う経路、対処・更新検証まで確認する。スキャナ警告だけで製品の脆弱性と断定しない。既存CIを先に調べ、なければverify/build/配布consumerを動かす最小構成を追加する。workflowファイルの存在だけでなく、対象revisionで成功し、意図的な境界違反を拒否する実行記録を要求する。有料モデル評価は通常CIへ入れない。

評価経路は削除を目的に統合しない。legacy decision/E04は過去結果の診断、pipelineは本体経路、extractionは既存基準と役割を明記する。実際の重複修正が必要になった箇所だけ共通化し、典型的な変更1件で影響箇所と検証が局所化したことを示す。

### Q06 Q07 強い根拠を必要とする検証

全17更新種別と公開read/usageを、入力検査、Scope、版、墓標、再送、投影、拒否前DML、例外後rollbackの行列へ対応付ける。全組合せを機械的に増やすのではなく、重要な状態遷移とリスクをカバーし、除外理由を記す。

実ファイルWALで単一writerを維持したまま、readonly reader、古いreceipt、取消、訂正・forget・restoreとの競合窓を試す。通常書込みの各DML位置、依存登録前後、checkpoint確定前後、commit前後で失敗・process終了を起こし、再オープン後の台帳・投影・epoch・進捗・再送結果を確認する。破損や失敗を無視して成功にするstubは作らない。

負の対照は、鮮度脱落、墓標チェック省略、途中更新の取り残し等の意図的な変異を隔離コピーで一時的に入れ、対応試験が失敗すること。製品ソースへ変異を残さない。

復旧実演はWorld単独のconsumerとtest hostで先に行い、H/M境界の実契約でも必要なケースを確認する。実Memory journalや実hostの操作をfixtureで代替して完了にしない。外部変更の許可・環境が不足する場合は、その証拠に依存するアンカーを上げずQ08へ報告する。既存の24時間・複数Scope運用基準は別に維持し、80点を全面的な本番受入と同義にしない。

## 5 Claude APIとLuna APIの使い方

2026年11月5日に確認した公式仕様に基づく推奨構成。アカウントでの利用可否は接続確認で確定し、利用不可でも別モデルへ黙って置換しない。

| 用途 | OpenAI | Claude |
|---|---|---|
| モデル | `gpt-6-luna` | `claude-sonnet-5-5` |
| 接続 | OpenAI Responses API | Anthropic Messages API |
| 出力形式 | 対応可能な共通schemaを `text.format` へ渡す | 同じ意味のschemaを `output_config.format` へ渡す |
| 抽出 | 同じ原典・entity候補・predicate・共有指示 | 左と同じ |
| 根拠選択と回答 | 各抽出モデルの出力を両方読ませる | 左と同じ |
| 補助的な意味評価 | Claudeの回答を評価 | Lunaの回答を評価 |

Lunaは `reasoning.effort=medium` を初期案とし、Sonnetのeffortも明示してdevで固定する。両社で同じeffort名が同じ計算量を意味するとは扱わない。対応が確認できないtemperature・seedを無理に送らず、モデル内の比較条件、APIが受け付けた設定、未指定項目を記録する。

既存ChatCompletionsProviderはtemperature 0のchat形式であるため、Lunaへ無変更で流用しない。既存decisionの実接続もOllama向けであり、Claude接続として扱わない。追加候補は `eval/extraction/openai-provider.ts`、`claude-provider.ts` と、decision/pipeline側の薄い接続。これらは計画上の名前で、現在の既存APIではない。

既存の共有指示、候補検査、明示採用、公開SQLite API、Slice/receiptを再利用する。APIに渡すJSON Schemaと製品契約の差は構造の接続に限定し、意味を変えるnull補完、引用補正、条件補完、壊れたJSONの意味修復はしない。両社のschema対応が異なる場合はdevで仕様を解決して両armを固定し、失敗後に一方だけJSON modeへfallbackしない。

新しいAPI評価は最初の生成で採点し、JSON再生成・回答修正を行わない。既存Ollamaの訂正1回経路は過去仕様として保持し、新しいAPI比較と混ぜない。HTTP/APIエラー、拒否、出力上限、timeout、無効な候補、請求量不明を別状態で記録する。接続は最大2並列、1要求120秒、回答不能を成功にしない。

公式資料ではLunaの現行snapshot名は `gpt-6-luna`。存在しない日付付きIDや重みdigestを作らず、要求・返却model、日時、API/SDK版、設定、取得可能なfingerprint・request IDを保存する。Claudeの現行model IDは固定snapshotとして扱えるが、serving環境の完全不変までは保証しない。[OpenAIモデル仕様](https://developers.openai.com/api/docs/models/gpt-6-luna)、[Claudeモデル仕様](https://platform.claude.com/docs/en/models/sonnet-5-5/overview)、[Claudeの版管理](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions)

出力の構造適合と意味の正しさは別判定にする。[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Claude Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

### 個人シェルのAPIキーを共用する

キーの正本は利用者の `~/.zprofile`。今回、値を複製せず次の参照を追加し、ログインシェルの子プロセスで両標準名が設定済みで元の値と一致することを確認した。

```sh
export ANTHROPIC_API_KEY="${ANTHROPIC_API_KEY:-${CLAUDE_API_KEY:-}}"
export OPENAI_API_KEY="${OPENAI_API_KEY:-${OPEN_AI_API_KEY:-}}"
```

標準名が既に非空ならその値を優先する。将来のadapterは `OPENAI_API_KEY`、`ANTHROPIC_API_KEY` を読み、必要に応じて利用者の元の名前もfallbackとして認識する。値を引数・レポート・例外へ出さず、環境変数全体もdumpしない。

既に起動したCodexやGUIは新設定を継承していない場合がある。評価コマンドは次の形式でログインシェルから起動する。`<評価コマンド>` はQ04で接続・予算の入口を実装した後に、実在するCLIへ置き換える。

```sh
zsh -lc '<評価コマンド>'
```

プロジェクトごとの `.env`、キーのrepo保存、製品設定の読取りは不要。CIで有料評価を別途動かす場合はその実行環境のsecret設定を使い、個人のzprofileをCIへコピーしない。通常CIはキーなしで全件検証できる状態を維持する。

## 6 モデル比較の設計

### 抽出の既存基準と独立補助群

既存 `ext-ja-v2` のdev100/holdout100、全200件を両モデルで実行する。current指示v2、`ext-threshold-v2`、dataset・採点器は維持する。precision、保留recall、区分正解率、採用recallはいずれも既存の19/20以上。Scope漏洩、引用捏造、忘却後復活、hypothesisの実測化は0許容のまま。

過去に参照されたholdoutを新しい未見証拠とは呼ばない。追加の独立60件を、訂正、条件、時点・履歴、曖昧対象、Scope/命令混入、忘却・遅着の6群×10件で先に固定する。既存dev/holdoutの文骨格・固有名詞の差替えだけで作らず、history目的の結果はcurrent評価と別に報告する。指示調整は既存devと通し仕事のdevだけで行い、独立60件を調整へ戻さない。

独立補助群と通し仕事のevaluationへ触れる前に、baseline/candidateの両版を固定する。片方の評価結果を見て他方を調整しない。新しい調整が必要なら、その集合は以後既知と記録し、次の独立評価を別に用意する。

独立補助群の採否も率95%以上、0許容違反なし、欠測0を事前条件にする。ただし小さい群別の率は診断値とし、標本から一般化しすぎない。条件式の意味、期間の境界、引用の意味支持は追加の構造検査・盲検意味評価で確認し、既存の疎な採点が合格しただけで十分とはしない。

既存holdout監査のstart/finish、失敗を分母へ残す規則、raw要求・生成文の非保存を維持する。独立抽出60件にも同じ非保存方針を適用する。devは最初の要求/出力を記録してモデル要求0で再生できるようにする。

### 既存20仕事は診断として維持する

既存20仕事×4条件を両モデルで実行し、従来の手書きWorldと採点器をそのまま診断する。原典外知識が混ざる限界、語句採点の言い換えへの弱さを記録する。結果を新しい通し評価と合算せず、手書きの高得点を自動抽出の効果へ流用しない。

### 本体経路で抽出と読み手を交差させる

新しい独立仕事40件をdev10/evaluation30に分け、根拠の位置・条件・時点・連鎖・無関係情報・十分な原文だけで答えられる対照を含める。authoring時に各正解の根拠が原典にあることを確認する。原典にない運営者知識を使うなら確認済みsourceへ追加し、全比較armへ同じ情報を与える。

抽出役には質問・gold・採点軸を見せない。Luna抽出／Claude抽出のそれぞれを、Luna読取り／Claude読取りへ渡す **2×2の交差比較** にする。抽出後はprepare/validate→inbox/candidate.settle→明示採用→readWorldSnapshot→buildWorldSlice→公開前のusage検証を通す。

採用は既存の確認済み操作・登録規則を使用し、引用一致やgold一致だけでactiveへ上げない。根拠選択はLLMが許可済み候補からID・版を提案し、codeは権限・版・上限を検査する。入力不足、候補0件、未採用、未取得、予算不足は失敗段階として残す。

| arm | 入力 | 比較で確認すること |
|---|---|---|
| raw-budget | 原典を事前固定した方式で同じ予算へ収める | 整理・選択を含むWorld経路全体の効果 |
| plain | Worldと同じ選択済み主張・引用・条件・期間・状態を平文で提示 | 情報量と根拠が同じときの表示・構造の差 |
| World | 本体Sliceを根拠・coverage・版情報付きで提示 | 条件や不確かさを使った回答が成立するか |
| oracle | goldが指定する必要根拠だけを提示 | 抽出・取得・選択と読み手の失敗を切り分ける診断 |

現在のpipelineのplainとWorldはkind以外同じ構造なので、そのままでは枠組みの比較にならない。新しいplain表示は同じ事実・条件・出典・診断を保った平文表現として先に定義し、情報差を監査する。ここで差が無ければ構造の優位は未実証と報告する。既存decisionの条件を落とすplainとも区別する。

主比較の文脈上限は最終表示全体8192 UTF-8 bytes以下。質問・指示・schemaを含む要求全体も別に計測する。同じbytesを同じtokenとは呼ばず、両APIの実usageを併記する。任意単位の切詰め規則と提示順を事前固定し、必須単位が入らないときはoverflowとして分母に残す。oracleは採用判定へ混ぜない。

raw-budgetは利用可能ならhostの既存原典検索を再利用し、その検索条件も両版で固定する。単純な直近切詰めを使った場合はその対照に対する差と明記し、一般的なRAG全体への優位に広げない。原典側にも検索・選択のモデル要求を追加する場合は、同じ資源条件と追加費用を先に計画へ反映する。

追加の品質条件は、4つの抽出役×読取り役の組合せを平均せず個別に判定する。

- WorldのScope漏洩、根拠のない断定、仮定・伝聞の実測化、忘却後の再採用は全40件で0。
- World対raw-budgetは、evaluation30件で改善5件以上、全40件で悪化0。全armの欠測・比較不能・未解決判定は0。改善・悪化の軸別定義は既存decisionと揃える。
- World対plainは同じ定義で別表にする。評価で改善5件以上かつ全40件の悪化0のときだけ、この集合での構造・表示の寄与を示したと記す。未達なら構造の優位を主張しない。
- 必要根拠recall、条件保持、期間境界、保留・引用の成績を段階別に報告する。改修候補は同じモデル・同じ予算の対照から既存成功と安全指標を下げず、対象だった欠落を改善する。

これらは追加のAPI評価条件であり、既存A46/A50の置換ではない。評価40件は統計的な一般化の証明ではなく、再評価へ提出する具体的な証拠とする。

### 意味評価と不一致の扱い

まず既存の決定的な採点を実行する。さらに独立仕事のevaluation30件のplain/World回答を、回答生成と異なる会社のモデルで評価する。モデル名、arm、baseline/candidateのラベルは隠し、順序を均等に入れ替える。事前のrubric、原典、必要な確認条件だけを渡す。

補助judgeは条件・引用の意味支持・根拠外断定を理由付きで返し、スコアの最終権限にはしない。全不一致・安全候補と事前固定した20%の無作為標本を人が確認する。既存の0許容違反をjudgeの高評価で消さず、未解決は不合格。採点器を変更する場合は別版として旧結果を残し、同じ新評価器で対照も取り直す。

## 8 証拠の保全と検証順

1. Q00で変更前srcを固定コピーへ保存し、改善対象を再現する。既存M0〜M3を作り直さない。
2. Q04のadapter・評価器・新しい表示形式を先に確定し、その同じharnessへ変更前srcと候補srcを載せて比較する。harness変更前のrunとの数値差を改善量にしない。
3. 各票の純粋・専用試験→実SQLite/domain結合→ `bun run verify` → `bun run build` を実施する。配布変更はconsumer、schema変更はmigration/backfill/restoreを必須とする。
4. 全体検証後の固定コピーでモデル比較と性能を実施する。ソース変更を検出したrunはinvalidatedとして保存し、採用根拠にしない。
5. 最終差分を確認し、個別の語句・質問・資料IDへの専用分岐、意味判断のコードへの移動、無関係な変更が増えていないか点検する。
6. Q08で新しいCurrent台帳を作り、同じ採点器で正式スコア・項目別根拠・適用範囲を計算する。

M0の厳格な比較は同じモデル・設定・datasetのbaseline/candidateへ使う。異なるprovider/modelの結果を既存compareで無理にcomparableへ変えない。モデル間は同一仕事の層別表として報告し、本文・code・schema・prompt・価格表・dataset・rubricのhashを残す。

現状のM0はpipelineをモデル不要のfixtureとして実行する。Q05の外部モデル通し評価は追加作業であり、既存コマンドがすでに対応しているとは扱わない。usageや結果schemaを拡張する場合は、既存report/replayとの互換と検証を同じ票に含める。

成果物は `artifacts/quality-80/<run-id>/` の新規ディレクトリへ追記専用で保存する。manifest、sourceの前後hash、request/schema/prompt digest、条件、実行環境、モデルID、失敗・費用、元レポート、標準出力・終了code、比較結果を含める。holdoutの本文・raw出力・APIキーは保存しない。再生はfixtureと明記する。

既存の性能基準は、1万主張のSlice p95<=50ms、通常writer p95<=20ms。1千/1万/10万主張で単独runを複数回行い、raw標本、partial、取得/展開行数、出力bytes、索引、rebuild、RSSを報告する。20万head/200001件は既存計画の上限境界として確認し、通常readの速度と再構築時間を混ぜない。

## 9 停止条件と再評価

同じ目的の「仮説・実施・結果確認」が3ラウンド続いた場合、現在の要求・計画・完了条件に照らして増えた証拠と減った残作業を整理し、次の編集・再実行の前に利用者へ短く通知する。新しい根拠のない同一失敗、検証中の編集、計画からの逸脱があれば3回を待たずに見直す。正常な長時間処理を時間だけで停止しない。

モデル版・利用枠・送信可能な資料・予算・外部契約のどれかが不足する場合、その依存票を停止し、独立するコード/fixture検証は進める。holdoutを見た後の調整は新しい評価集合・版へ分け、既存の閾値・期待値を下げない。

Q08では、正式80点以上なら対象snapshotと証拠を示して完了とする。80点未満なら達成扱いにせず、実際の点数、未達アンカー、原因、次の最小票と必要資源を報告する。追加票はその観測結果から決める。プロジェクトの将来性は、実仕事の成果・導入負担・継続利用が得られた時点で別に再評価する。
